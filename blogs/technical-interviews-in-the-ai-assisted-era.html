What Are We Actually Testing? Technical Interviews in the AI-Assisted Era

A measurement framework for evaluating technical judgment when code generation is no longer the scarce part of the work.

PublishedAugust 13, 2026Last reviewedAugust 13, 2026StatusWorking paper

Thesis. Allowing or prohibiting AI is not the core interview decision. The core decision is what capability the interview intends to measure, under which tool and data boundaries, and how the company will verify the candidate’s judgment.

01Abstract

Large language models can generate, debug, explain, and optimize code in seconds. That changes the relationship between a timed coding test and the work many engineers now perform. Some companies permit AI-assisted coding in assessments and case studies. Others prohibit it so they can isolate independent reasoning and implementation fluency. Neither position is automatically correct or outdated. Each creates a different measurement environment.

The more useful question is not, “Should candidates use AI?” It is, “What evidence would demonstrate success in this role?” If the job requires architecture, system decomposition, code review, testing, data judgment, security awareness, and accountable use of AI, an interview should measure those capabilities directly. If the job also requires independent debugging or operation in restricted environments, the process should isolate that baseline explicitly rather than hiding it inside an ambiguous policy.

02AI policy is measurement design

An interview rule changes the signal the company can observe. A no-AI exercise can reveal baseline fluency, code comprehension, debugging discipline, and the candidate’s ability to work when external assistance is unavailable. It can also overemphasize memory, syntax recall, puzzle familiarity, and performance under artificial time pressure.

An AI-allowed exercise can resemble modern development more closely. It can reveal how a candidate decomposes work, delegates tasks, writes constraints, reviews generated changes, designs tests, and recovers from incorrect output. It can also accidentally measure familiarity with a specific tool, access to paid accounts, prompt style, or willingness to accept suggestions quickly.

Principle: an AI rule is not a moral statement about engineering competence. It is an experimental condition. The interview designer must explain what that condition is intended to measure.

03The current market is already split

Current interview platforms illustrate several philosophies rather than one settled standard. CodeSignal documents an agentic-interview format in which candidates can use coding agents and teams evaluate collaboration, guidance, review, validation, and problem solving. HackerRank documents guarded and unguarded AI-assistant modes selected by the hiring company, with interviewer visibility into AI interactions. Karat’s AI-enabled format uses an integrated assistant inside realistic codebases and evaluates communication, product sense, systems thinking, and the candidate’s ability to direct and refine generated code.

At the same time, Anthropic has documented repeatedly redesigning a technical take-home because stronger models removed the distinction between candidate performance levels. Its engineering team uses both AI-resistant design and explicitly AI-compatible longer-horizon tasks, depending on the signal needed. GitHub has long argued that take-home interviews should resemble day-to-day work, including preferred tools, internet access, automated tests, and clear rubrics. OpenAI’s public interview guide emphasizes design quality, code quality, performance, test coverage, communication, and collaboration.

These examples do not establish a universal best practice. They show that technical interviewing is becoming a design space with several legitimate operating modes.

04Four interview modes

ModeAI boundaryBest signalMain risk
Closed-book fundamentalsNo generative AI; limited or declared documentationIndependent fluency, comprehension, debugging, basic algorithmsLow resemblance to normal work; memory and puzzle bias
Guarded assistanceSyntax, navigation, or conceptual help; no full solution generationBaseline skill with bounded supportUnclear boundaries and inconsistent enforcement
Open AI-assisted engineeringIntegrated agent or copilot; interactions loggedDecomposition, delegation, verification, testing, productivityTool familiarity and access can distort comparison
AI-native systems caseAI expected within a realistic repository and product scenarioArchitecture, product judgment, data and governance decisions, operational ownershipHarder to standardize and score consistently

These modes can be combined. A strong process does not need to choose between fundamentals and realistic AI-assisted work as though they were mutually exclusive.

05The scarce skill has moved up the stack

When code generation becomes inexpensive, value shifts toward deciding what the code should do and whether the result is safe to own. The interview should therefore create opportunities to observe:

  1. Problem framing: Does the candidate clarify the user, objective, constraints, and definition of success?
  2. Architecture: Can the candidate separate components, interfaces, state, failure modes, and external dependencies?
  3. Implementation judgment: Can the candidate choose an appropriate level of abstraction rather than generating unnecessary complexity?
  4. Evaluation: Do tests cover normal behavior, edge cases, regressions, security conditions, and incorrect AI output?
  5. Data and governance: Does the candidate recognize privacy, access, retention, lineage, model, and policy boundaries?
  6. Communication and ownership: Can the candidate explain trade-offs, identify uncertainty, and defend or revise the solution?
  7. Degraded-mode fluency: Can the candidate still reason and debug when AI, the network, or a preferred tool is unavailable?

This is the core of the argument: the modern skill is understanding what to build, why it matters, how to evaluate it, and how the company’s data and governance posture shapes the implementation.

06A staged interview design

A practical process can separate signals instead of asking one exercise to measure everything.

1. Fundamentals calibrationA short code-reading, debugging, or implementation task without generative AI. The goal is a baseline, not an obscure algorithm contest.
2. AI-assisted repository taskA realistic codebase, clear requirements, a standardized integrated assistant, and enough time to plan, implement, test, and document.
3. Review and defenseThe candidate explains architecture, accepted and rejected suggestions, tests, risks, and trade-offs. The interviewer introduces a changed requirement or failure case.
4. Role-specific deep diveData, security, performance, product, ML, infrastructure, or domain questions aligned to the actual responsibilities of the role.

This design recognizes both independent capability and AI-enabled performance. More importantly, it prevents a candidate from passing solely because the generated artifact looks polished.

07An illustrative evaluation rubric

DimensionSuggested weightEvidence to observe

The percentages are illustrative. A performance-engineering role, data-platform role, security role, or product-focused engineering role should weight them differently. The important practice is to publish the dimensions before evaluating candidates.

08Evaluate the process, not prompt theater

AI-assisted interviewing should not become a contest for the longest prompt or fastest acceptance of generated code. Useful evidence includes the candidate’s plan, the tasks delegated, suggestions rejected, tests added, diffs reviewed, assumptions challenged, and corrections made after a failed result.

A candidate should be able to explain every material part of the submitted solution. “The model wrote it” is not ownership. At the same time, manually retyping a correct suggestion should not be rewarded as proof of deeper competence.

Review rule: score decisions and verification. Do not score theatrical independence or blind tool enthusiasm.

09The company’s data posture belongs in the interview

AI use cannot be separated from the organization’s security and governance model. An interview for a company that prohibits external models on proprietary code should not reward behavior that would violate that policy at work. A company with an approved internal assistant should evaluate whether candidates can use that environment safely and effectively.

The interview design should therefore declare:

  • Which AI tools and models are allowed, optional, required, or prohibited.
  • Whether external accounts, network calls, extensions, or local models may be used.
  • What interview code, prompts, and telemetry are retained and who can review them.
  • Whether the provided repository contains synthetic data only and whether any content may leave the environment.
  • How secrets, credentials, customer information, and proprietary source code are excluded.
  • Which company policies the scenario is designed to represent.

This makes governance part of engineering judgment rather than a compliance appendix added after hiring.

10Fairness and candidate transparency

AI-enabled interviews create new fairness risks if candidates arrive with different tools, subscriptions, hardware, network quality, or prior exposure. A defensible process should provide the same environment, model access, time budget, repository, and instructions to every candidate—or explicitly normalize for differences.

  • Disclose the AI policy before the interview, not after the candidate begins.
  • Provide the approved tool rather than requiring a personal paid account.
  • Explain whether AI usage is optional and how non-use will be evaluated.
  • Offer an accessible alternative when the interface or interaction mode creates a barrier.
  • Use a written rubric and train interviewers on consistent scoring.
  • Keep the task time-bounded so candidates with more free time do not gain an unlimited advantage.
  • Avoid proprietary or personal data and explain logging and retention.

11What each policy reveals about the company

A no-AI interview may indicate that the company values independent fluency, works in restricted environments, or wants a clean baseline before evaluating tooling. An AI-allowed interview may indicate that the company values modern productivity, delegation, review, and fast iteration. A mixed process may indicate that the company expects engineers to operate in both modes.

The problem is not choosing one philosophy. The problem is choosing one accidentally, enforcing it inconsistently, or using it to measure a role that works differently in practice.

12Questions candidates should ask

Candidates also need clarity. Useful questions include:

  • Which tools are permitted, and is AI use expected, optional, or prohibited?
  • Will prompts, accepted suggestions, terminal activity, or screen recordings be reviewed?
  • What part of the exercise is intended to measure independent coding?
  • How are AI-generated mistakes, candidate corrections, and testing behavior scored?
  • What data-security or confidentiality constraints should be followed?
  • Is the rubric focused on the final artifact, the reasoning process, or both?

Preparing for modern interviews therefore means practicing architecture explanation, code review, test design, failure analysis, and governance reasoning—not only algorithm recall or prompt construction.

13Conclusion

The timed coding test does not need to disappear. It needs a narrower job description. It can establish a baseline, but it should not be mistaken for a complete model of engineering performance.

In an AI-assisted era, the strongest signal is not how quickly someone can produce code in isolation. It is whether they can frame the right problem, design a sensible system, use tools proportionally, verify the result, respect data and policy boundaries, communicate trade-offs, and take responsibility for what ships.
