What Are We Actually Testing? Technical Interviews in the AI-Assisted Era

My view on what an interview should measure when code generation is no longer the scarce part of the job.

PublishedAugust 13, 2026Last reviewedAugust 13, 2026StatusWorking paper

01Why I wrote this

Some companies encourage candidates to use an assistant because that is how the team works. Others prohibit it because they want an independent baseline. Both choices can make sense. The rule becomes weak when nobody can explain what it is meant to measure.

02AI policy is measurement design

A no-assistance task can reveal code reading, debugging, and independent fluency. It can also overvalue memory and puzzle practice. An assisted task can reveal decomposition, delegation, review, testing, and recovery from bad output. It can also reward familiarity with one product.

The company should be able to finish this sentence: “We chose this condition because we want to observe...”

03Four interview modes

04What I would measure

  • Does the candidate clarify the user, objective, constraints, and definition of done?
  • Can they split the system into useful components?
  • Can they review generated code and explain the final implementation?
  • Do the tests cover normal behavior, edge cases, and regression risk?
  • Can they explain trade-offs and change direction when evidence changes?
  • Can they still reason when the assistant is unavailable?

The skill I care about is knowing what to build, why it matters, how to evaluate it, and how the company's data and governance posture changes the answer.

05A staged interview design

  1. A short fundamentals check without generative assistance.
  2. A realistic repository task with a standard assistant.
  3. A review conversation about the design, accepted and rejected suggestions, tests, and risks.
  4. A role-specific deep dive into data, performance, product, or infrastructure.

06A sample rubric

DimensionIllustrative weight
Problem framing and product sense15%
Architecture and decomposition20%
Correctness and testing20%

Data and governance judgment15%
Communication and ownership15%

07The company’s data posture belongs in the interview

The instructions should say which tools are allowed, whether use is optional, what activity is reviewed, and how long records are retained. Every candidate should receive the same environment and access.

08Where I land

A timed coding test can establish a baseline. It should not pretend to represent the whole job. The stronger signal is whether someone can frame the problem, design a sensible system, verify the result, respect the company's working boundaries, and own what ships.
