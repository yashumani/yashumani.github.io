Working paper / Systems evaluation

AI-Powered Systems vs. AI-Generated Outputs

A revised framework for evaluating artifacts, workflows, systems, and managed AI capabilities without confusing polished generation with accountable operation.

PublishedAugust 2, 2026Last reviewedAugust 12, 2026StatusWorking paper

Thesis. AI-generated describes an artifact’s origin; AI-powered describes AI’s role in a capability. Accountability depends on the layer being claimed and the evidence surrounding it.

01Abstract

Organizations often use the same label for two different things: a model-generated artifact and a system that uses AI inside an accountable workflow. The distinction should not be based on whether the final output was generated by a model. It should be based on the unit of evaluation. An artifact is evaluated primarily as a result. A system is evaluated across inputs, ownership, controls, evidence, operating behavior, and outcomes.

This revised framework treats AI-generated and AI-powered as overlapping descriptions rather than mutually exclusive categories. A production system may generate text, code, images, predictions, or recommendations. It becomes accountable when the surrounding workflow can be governed, measured, inspected, and improved.

02The evaluation unit

The simplest correction is to stop asking only, “Did AI create this?” and ask, “What exactly are we evaluating?”

ArtifactA discrete answer, draft, image, code fragment, summary, or recommendation.
WorkflowA repeatable sequence that transforms inputs into reviewed outputs.
SystemSoftware, data, models, controls, users, and operational dependencies working together.
Operating modelOwnership, policy, monitoring, escalation, maintenance, and improvement around the system.

An artifact can be excellent without proving a reliable workflow. A workflow can be well designed without proving production operations. The evaluation language should match the layer being claimed.

03A four-layer maturity model

LayerPrimary questionEvidenceCommon failure
Generated artifactIs the result useful and correct?Human review, task score, factual checkPolished output mistaken for system proof
Repeatable workflowCan the process be repeated consistently?Defined inputs, steps, tests, structured outputsPrompt logic hidden in ad hoc usage
Accountable systemCan behavior be traced, controlled, and measured?Architecture, logs, evaluation, access controls, failure handlingModel quality treated as the only quality dimension

04The accountability test

A practical test has six questions:

  1. Purpose: What decision or job is the system intended to improve?
  2. Owner: Who is accountable for the result and the failure modes?
  3. Boundary: Which steps are model-driven, deterministic, human-reviewed, or external?
  4. Evidence: What proves the output is grounded, reproducible, and fit for use?
  5. Control: What blocks, repairs, escalates, or rolls back a bad result?
  6. Outcome: What operating or user measure changes if the system succeeds?

If these questions cannot be answered, the work may still be a useful AI-generated artifact, but it should not be presented as a production-grade AI capability.

05Evidence should match the claim

Different claims require different evidence. “The interface exists” can be supported by a working preview. “The workflow is reliable” requires tests and failure-state evidence. “The system improves a business outcome” requires a valid baseline, measurement window, and adoption context.

Rule: never use implementation evidence to imply business impact, and never use a polished output to imply operational reliability.

This is why portfolio maturity labels matter. Live, source-complete, pre-validation, externally dependent, and proposed architecture are different states. Clear labels make the work more credible, not less ambitious.

06Applied across the portfolio

The portfolio demonstrates several variations of the framework:

  • Agentic Knowledge & Research Runtime: generation is surrounded by retrieval, evidence graphs, critique, repair, evaluation, and durable orchestration.
  • Automated ML Pipeline Platform: automated model selection is governed by data preparation, candidate search, holdout evaluation, lineage, and registration.
  • My Seventh Meal: a multimodal model proposes meal candidates, while user confirmation and deterministic nutrient logic define the final calculation.
  • Mangrok: AI culinary analysis is separated from encrypted secret handling, entitlements, storage policies, print operations, and human legacy review.
  • Drill-down Anomaly Lab: conversational analysis is constrained by quality-approved dimensions, cohort state, deterministic variance calculations, and explicit causal limits.

07Current governance context

NIST’s AI Risk Management Framework remains a useful organizing model for governance, mapping, measurement, and management. NIST states that AI RMF 1.0 is being revised, so a working paper should not imply that the 2023 document is frozen indefinitely. The Generative AI Profile, NIST AI 600-1, remains a companion resource focused on generative-AI risks and actions.

The implication for system design is practical: testing, evaluation, verification, validation, content provenance, incident disclosure, and lifecycle governance belong around the model. They are not optional decorations added after a demo.

09Limits and anti-patterns

The distinction should not become a marketing shortcut. An AI-powered system can still be poorly governed. A deterministic system can still use bad data. A human-in-the-loop label can still hide unclear accountability. More components do not automatically create more trust.

The goal is proportional evidence. A low-risk internal helper may need lightweight review and logging. A health, finance, employment, or high-impact workflow needs stronger controls, clearer limits, and more rigorous evaluation.

10Conclusion

AI-generated describes how an artifact was produced. AI-powered describes how AI participates in a broader capability. The more useful distinction is the layer of accountability being claimed.

A serious system should make its purpose, owner, model boundary, deterministic controls, evidence, failure handling, and outcome measurement visible. The model may generate the output, but the system must own the process.
