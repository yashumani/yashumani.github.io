The problem it addresses

Connecting a language model directly to raw documents does not create a reliable organizational brain. A query can return a number while still omitting the metric definition, calculation grain, lineage, owner, business rules, access restrictions, caveats, prior decisions, and source evidence needed to interpret it safely.

The project creates that missing middle layer. It treats enterprise knowledge as a governed product that can be compiled, reviewed, versioned, retrieved, and reused across many AI experiences.

Context is the durable product

The core design principle is that answers are temporary outputs, while approved context is the reusable asset. A brain object can represent a metric, dataset, report, business rule, owner, system, decision, narrative template, or relationship between them.

  • Evidence remains attached — source documents, chunks, tables, SQL artifacts, dashboard metadata, and other evidence objects remain traceable instead of being replaced by an unreviewable summary.
  • Ontology supplies the grammar — knowledge is normalized into explicit entity types and relationships such as metric ownership, calculation lineage, report usage, and governing business rules.
  • Context packs are consumption units — downstream applications receive approved definitions, rules, caveats, related objects, access decisions, confidence, freshness, and source evidence for a specific question or task.

REST, MCP, SDK, and CLI share one core

The REST API is the product and platform backend. The MCP server is a thin adapter for AI clients and agents. A Python SDK supports notebooks and backend services, while the CLI supports local workflows and GitLab jobs.

CompilerService + GovernanceService + RetrievalService + ContextPackService + BrainStore → REST API / MCP adapter / Python SDK / CLI

No adapter owns separate business logic. MCP tools call the same services and policy checks as the REST API, so an agent cannot bypass review or authorization simply by using a different transport.

Governance workflow

Raw source material → evidence → candidate knowledge → human review → published brain object → permission-aware context pack

  • Candidate creation — parsers, deterministic rules, plugins, or optional AI providers classify and normalize source material into candidate objects.
  • Review state is explicit — draft, submitted, AI-classified, human-review-required, approved, rejected, published, and deprecated states make maturity inspectable.
  • Publishing is controlled — AI-generated suggestions and plugin output cannot become official knowledge without the same human-governance path.
  • Audit evidence survives — source references, confidence, warnings, sensitivity, owner, reviewer, and freshness metadata remain part of the record.

Offline-first AI and plugin architecture

The brain remains useful when the internet and hosted models are unavailable. AI is a pluggable accelerator rather than a runtime dependency.

Offline, no modelYAML and Markdown objects, deterministic validation, rule-based classification, local review, keyword retrieval, and context-pack generation.
Offline, local AIOptional local services can classify, summarize, extract, embed, rerank, or draft review notes while the governance boundary remains unchanged.
Hosted AIApproved enterprise providers can improve extraction, conflict explanation, narrative generation, and reasoning only where policy permits.
HybridLocal AI handles default work and hosted AI is reserved for explicitly approved tasks.

Plugins can add source connectors, parsers, extractors, validators, retrievers, context-pack decorators, policy rules, and exporters. The starter includes a create-ukb-brain package skeleton, a brain.config.yaml template, built-in plugin contracts, and an offline local-brain example.

Security boundary

Security filtering must occur before context reaches a model. The safe sequence is identity → policy check → allowed retrieval → context-pack composition. “Retrieve everything and ask the model not to reveal it” is explicitly rejected.

Public-repository boundary

The scaffold uses synthetic examples only. Real company documents, dashboards, source data, credentials, customer data, and workplace-only context belong in a private enterprise deployment with approved identity, secrets, storage, audit, and network controls.

Current implementation

  • FastAPI service — health, ingestion, review, brain-object, context-pack, and audit endpoints.
  • MCP adapter — tools for context submission, review queue access, approval, search, and context-pack retrieval.
  • Shared contracts and services — Pydantic models plus compiler, governance, retrieval, context-pack, store, plugin, and provider abstractions.
  • Starter distribution — npm-style brain generator, YAML configuration, domain examples, local plugin example, Docker, Docker Compose, Makefile, and GitLab CI starter.
  • Demo and documentation — architecture, API-versus-MCP, governance, context-pack, offline-first, plugin, security, deployment, roadmap, browser slides, and animated-diagram materials.

Next build

The scaffold intentionally stops before claiming enterprise production readiness. The next development cycle is to replace the in-memory store with durable infrastructure and make review and relationship exploration usable through a product interface.

  • Postgres for evidence, review state, knowledge objects, policy metadata, and audit history.
  • Object storage for original source evidence.
  • Keyword, vector, and hybrid retrieval with graph relationships and lineage traversal.
  • Real authentication, ACL inheritance, sensitivity filtering, and enterprise SSO integration.
  • A React governance workspace with submission, review, conflict resolution, and an Obsidian-style relationship graph.
  • Source connectors added one at a time with explicit offline and network requirements.
