THREAD — Trusted Analytics for Decisions

The enterprise problem

A question such as “Why did this KPI change?” can cross dashboards, spreadsheets, metric definitions, access rules, SQL, analysts, and AI assistants. Every handoff creates an opportunity to lose business meaning, use the wrong grain, expose restricted data, or return a confident answer without sufficient evidence.

The hard problem is not text-to-SQL or chart generation in isolation. It is maintaining semantics, authorization, source boundaries, verification, and provenance throughout the decision process.

The product principle

Fail closed

If THREAD cannot verify an answer, it should clarify, deny, reject, report that no source is ready, or abstain. Fluency is never treated as evidence.

The system separates language interpretation from deterministic controls. A model may interpret wording, while approved definitions, access policy, query compilation, connector limits, result checks, and evidence receipts control what can be released.

One governed thread

01 / Ask

Capture the business question, user context, reporting period, comparison, and ambiguity that may require clarification.

02 / Govern

Bind the request to approved metric and dimension definitions, semantic versions, tenant policy, role, and data classification.

03 / Execute

Compile a deterministic Business Query IR and run parameterized, bounded, read-only queries through approved connectors.

04 / Verify

Check source coverage, freshness, limits, result sense, and numerical claims before an answer can be certified.

05 / Visualize

Select a usable chart pattern from a tested registry and keep the analytical purpose visible to the user.

06 / Decide

Return the answer with its definitions, query and result hashes, source receipt, and clear boundary on what the evidence supports.

Released community-alpha milestone

The completed milestone makes the project inspectable and useful for public contribution. It includes an Apache-2.0 license, DCO contribution process, governance and security guidance, ownership rules, issue forms, release metadata, exact-source deployment evidence, SBOM and provenance controls, and a documented contribution backlog.

  • 25 accepted visualization renderers available in the public studio with synthetic data.
  • 76 finite visualization types organized across eight delivery batches.
  • 51 defined contribution opportunities kept in the contributor backlog rather than exposed as unfinished product UI.
  • Search and analytical-purpose filters designed for end users, without implementation tracking on the public surface.
  • CSV demonstration, governed definitions, durable conversations, evidence receipts, and connector patterns for SQLite, PostgreSQL, BigQuery, and Parquet.
  • CI, CodeQL, dependency review, immutable action references, container evidence, Pages verification, SBOM, and provenance workflows.

Why the visualization program matters

THREAD treats visualization as part of analytical reasoning, not decoration after an answer. The implementation program reviewed Holtzy’s D3, R, Python, and React gallery families, deduplicated them into semantic targets, and converted the result into a finite product matrix. Only accepted and tested types appear in the end-user studio.

This structure gives contributors bounded work: each future type has a defined analytical purpose, acceptance contract, accessibility expectation, and test path.

What works today

Honest release boundary

Community alpha, not production SaaS

The completed claim applies to the public community-alpha milestone. The hosted studio is network-disabled and uses synthetic data. It is not a public data API, model proxy, hosted BigQuery connection, Internet-facing enterprise runtime, or production SLA.

Live provider acceptance, private identity activation, tenant infrastructure, operational ownership, monitoring, recovery objectives, and production approval remain the responsibility of a controlled deployment. The project documents those paths without representing them as already activated.

What I learned

Conversational analytics becomes credible when the conversation is the interface—not the control plane. The durable value comes from approved meaning, explicit authorization, bounded execution, visible verification, and evidence that survives beyond a persuasive answer.
