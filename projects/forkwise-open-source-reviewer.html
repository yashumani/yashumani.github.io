ForkWise — Open Source Reviewer

I built ForkWise because adopting an open-source repository is not the same as admiring its README or star count. The practical decision is whether a specific team should adopt it, pilot it, fork it, avoid it, or gather more evidence—and why.

Why I built it

Open-source evaluation often collapses into popularity, a quick README scan, or an unstructured security review. Those signals can be useful, but they do not answer whether the repository fits the intended use, how difficult it will be to operate, what the team will have to own, or how hard it will be to leave later.

ForkWise makes the decision context explicit, pins the review to an exact commit, separates evidence from interpretation, and keeps unsupported claims visible rather than converting them into confidence.

What the decision model evaluates

Fit

Whether the repository, documentation, packaging, and stated purpose match the intended use and contribution model.

Trust

License, repository state, security governance, dependencies, CI, credential signals, and supply-chain indicators.

Run

Runtime, database, queue, storage, credential, deployment, external-service, resilience, and operational requirements.

Own

Likely maintenance burden, test and documentation signals, technical breadth, and maintainer concentration.

Exit

Export, import, migration, API, replaceability, and lock-in signals that affect a future transition.

Context

The recommendation changes with the user’s purpose, deployment target, data sensitivity, team size, and external-service policy.

Logic flow

Adoption decision
  1. 01

    Describe intended use

    The reviewer captures purpose, use case, deployment target, data sensitivity, team size, and external-service constraints.

  2. 02

    Validate repository scope

    Unsupported hosts and URL forms are rejected before evidence collection begins.

  3. 03

    Pin the exact commit

    The review records the default branch and 40-character commit SHA so the result can be reproduced.

  4. 04

    Collect bounded evidence

    Metadata, the recursive tree, README, release information, and selected high-value text artifacts form the review snapshot.

  5. 05

    Check README claims

    Claims are marked verified, partial, unverified, contradicted, or not claimed based on inspected signals.

  6. 06

    Evaluate five dimensions

    Fit, Trust, Run, Own, and Exit are evaluated against the user’s stated constraints.

  7. 07

    Return a decision path

    The report recommends Adopt, Pilot, Fork, Avoid, or Insufficient evidence and records unresolved questions and a pilot checklist.

Architecture rules

Evidence boundaryPin facts to one commit before interpreting them
Execution boundaryInspect text and metadata; never run repository-controlled code
Release boundaryKeep hosted mode off until the complete job lifecycle is proven

README Reality Check

The reviewer does not treat documentation as either true or false. It compares common claims—such as fully self-hosted, easy container deployment, production ready, privacy focused, quick setup, or low lock-in—against the inspected repository snapshot.

  • Verified when the claim is present and supporting evidence is observed.
  • Partial when relevant evidence exists but the full claim is not established.
  • Unverified when the README makes the claim without enough inspected support.
  • Contradicted when inspected evidence creates a material conflict or exception.
  • Not claimed when the primary README does not make the claim.

Evidence and reproducibility

A report records the repository owner and name, default branch, exact commit SHA and URL, analyzer version, report schema version, generation time, normalized user context, evidence identifiers, and evidence URLs. Findings reference evidence rather than appearing as unsupported prose.

Coverage is based on independent evidence families, not popularity. Large or truncated trees and a small number of readable artifacts cap the confidence rather than being silently ignored.

Browser safety boundary

Static-only inspection

The public reviewer does not install packages, run tests, execute lifecycle scripts, start containers, execute workflows, render repository HTML, or run arbitrary application code.

Repository text is rendered as text, credential-like values are redacted, exports are validated again before serialization, and the review is limited to public github.com repositories.

Hosted runner and production path

The repository also contains a request-bound Node runner reference, asynchronous job contracts, a file-backed local store, PostgreSQL migration and lease semantics, a hardened container contract, a browser runner client, and an operator console.

That work is intentionally not represented as the normal production path. The hosted service can accept a job, but the deployed lifecycle still leaves accepted jobs queued. Issue #3 tracks the request-bound deployment; issue #4 blocks public hosted-mode activation until a real repository progresses through queued, running, and completed without duplicate execution.

Community preview and validation

Version 0.9.0 adds Apache-2.0 licensing, contributor governance, security and privacy policies, structured issue forms, DCO sign-off, CODEOWNERS, a pull-request template, maintainer guidance, and a public contribution backlog.

The recorded release evidence reports 41 JavaScript files passing syntax checks, four API documents and five paths passing contract validation, six workflows and 19 external actions passing immutable-reference checks, 23 community-readiness files passing validation, and 82 automated tests passing with zero failures. Separate main-branch gates covered quality, runner contracts and hosted health, database semantics, the hardened container, and GitHub Pages deployment.

What works today

  • Live GitHub Pages reviewer for public repositories.
  • GitHub-native responsive workspace and Actions-style progress experience.
  • Commit-pinned bounded static inspection and deterministic recommendations.
  • Fit, Trust, Run, Own, and Exit dimension summaries.
  • README claim ledger, evidence-linked findings, unresolved questions, and pilot checklist.
  • Validated JSON and Markdown exports.
  • Live operator console and hosted health/schema checks.
  • Public community workflow for false positives, false negatives, analyzer rules, documentation, accessibility, fixtures, and focused code contributions.

What it does not claim

  • Static indicators do not prove runtime behavior, performance, scalability, exploitability, legal compliance, or production fitness.
  • The reviewer is decision support, not a security certification or legal opinion.
  • Anonymous GitHub API limits and truncated trees can reduce evidence coverage.
  • Private advisories, organization settings, branch protection, and complete repository history are not comprehensively assessed.
  • Hosted analysis is not active for normal reviewer traffic.
  • Authentication, durable production workers, operational alerts, retention controls, backup and restore, and production release governance remain future work.

What I learned

A useful open-source review is not a universal score. It is a traceable decision made against a particular use case and operating constraint. The most important design choice was preserving the difference between evidence, a rule-based interpretation, and a recommendation that still belongs to the team making the adoption decision.
