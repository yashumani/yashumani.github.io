HarnessLab — Agentic Harness Builder

I built HarnessLab to answer a practical question: before an agent receives tools, memory, or permission to act, what harness should control it? The application turns a requirement into a versioned architecture, permission model, artifact contract, trace, and evaluation plan. It starts with deterministic analysis and adds one temporary critic only when a compatible gateway is explicitly running.

Why I built it

Agent demonstrations often begin with a model, a prompt, and a collection of tools. The harder questions arrive later: What context does the agent receive? Which actions are allowed? Which actions require approval? What state survives? What happens when a provider fails? Which artifact proves the work was completed? HarnessLab starts with those questions.

The central idea is simple: an individual agent can be replaced, but the harness should preserve the architecture, permissions, limits, evidence, and evaluation rules around it.

What works today

Requirement-to-architecture planning

The browser engine interprets the objective, constraints, risk, systems, and success criteria, then recommends deterministic software, an LLM feature, a workflow, a single agent, or a bounded multi-agent design.

Durable harness specification

The result records topology, protocols, planned agents, permissions, approval gates, artifacts, trace events, unresolved questions, and an evaluation plan in one validated structure.

Provider-neutral analysis

The application remains usable through its deterministic browser engine. An optional gateway can use its deterministic provider, an explicitly configured Ollama model, or OpenRouter's free-only route.

One executed temporary critic

A tightly limited architecture critic can review an existing harness plan through one provider call and return a typed review artifact. Provider advice cannot directly rewrite the control plane.

The harness is the durable layer

HarnessLab keeps the model-facing work inside a larger system contract. A generated plan is not complete until the platform can show the role of each component, the context boundary, allowed and denied actions, required approvals, expected artifacts, evaluation criteria, and failure behavior.

  • Requirements remain attached to the resulting architecture.
  • Planned subagents receive bounded responsibilities rather than open-ended autonomy.
  • MCP, A2A, retrieval, and typed-function choices are recommendations in the current planner, not claims of live protocol execution.
  • Structured artifacts carry work between stages instead of relying on unbounded agent conversation.
  • Trace and evaluation are part of the initial design rather than later observability additions.

The temporary architecture critic

The critic is the first temporary subagent HarnessLab actually executes. Its job is intentionally narrow: review one already validated harness plan and return one structured TemporaryAgentReview.

Fixed worker contract

One worker. One provider call. No tools. No child agents. No external actions. A fixed deadline. A whitelist-only context envelope limited to 48 KiB.

A finding is applied only when it passes the typed schema, has medium or high severity, and carries confidence of at least 0.70. Lower-confidence or lower-severity findings remain in the retained review artifact, but they do not change the harness.

The deterministic merge may add an unresolved question, a critic note, an evaluation dimension, trace evidence, and the review artifact. It cannot weaken permissions, denied actions, approval requirements, stages, protocol decisions, planned-agent contracts, existing constraints, artifact retention, or traceability.

Provider and credential boundary

The browser does not accept provider keys and cannot select a provider or model for the critic request. Provider configuration stays in the separately operated gateway.

  • Browser deterministic: no account, model download, gateway, or paid service is required.
  • Automatic fallback: the browser may use the gateway when it is reachable and fall back to deterministic analysis when the configured mode allows it.
  • Gateway required: analysis or critic execution fails visibly when the gateway is unavailable.
  • Ollama: a locally installed model can supply bounded guidance through the gateway.
  • OpenRouter: only openrouter/free or an explicitly named :free model is accepted; there is no paid-model override.

The public GitHub Pages site hosts the browser application. Actual model-backed analysis and critic execution require a separately running gateway.

Artifacts, trace, and workspace state

The result contract is designed to make the plan inspectable and portable. The browser workspace saves projects as immutable versions so a prior architecture can be restored without silently overwriting its history.

  • The original requirement is retained with each saved harness result.
  • The result includes architecture, protocols, permissions, planned agents, safety constraints, artifacts, trace, and evaluation.
  • Critic execution records provider, routed model, latency, context size, call budget, accepted findings, rejected findings, and failure evidence.
  • Users can copy or download results and export a JSON workspace backup.
  • Browser storage is local to the current profile. It is not encrypted cloud storage or cross-device synchronization.

What the current release does not do

Execution boundary

The current release does not execute MCP tools, A2A peers, arbitrary code, commands, files, databases, external writes, deployments, purchases, or production changes.

It also does not provide unrestricted autonomous operation, automatic paid-model use, authenticated cloud projects, tenant isolation, encrypted secret storage, or a general adaptive swarm. The current worker is one architecture critic with a fixed task and fixed limits.

Roadmap, not current-state claims

The product requirements describe a broader platform, but those items remain future work until implementation and test evidence exists.

  • Multiple dependency-aware temporary workers and an evaluator or judge.
  • Adaptive orchestration, concurrency, recursion limits, budgets, retries, fallbacks, and cancellation across a larger workflow.
  • Live MCP clients, native and REST tools, retrieval, GitHub, databases, and sandboxed file or command access.
  • Simulation, regression evaluation, failure injection, model comparison, and routing feedback.
  • Authentication, PostgreSQL-backed projects, tenant isolation, encrypted secrets, audit controls, environment separation, recovery, and load testing.
  • Implementation-scaffold export beyond the current portable harness JSON.

What I learned

Agency should be earned by the requirement, not added because the technology is available. The safest design is often a deterministic workflow with one narrow model-assisted seam. When a temporary agent is useful, its value comes from bounded context, explicit permissions, a typed artifact, and a deterministic gate that decides what survives.
